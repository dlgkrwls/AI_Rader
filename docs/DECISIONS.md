# 결정 기록

구현하며 내린 결정을 append-only로 기록한다. **위에서 아래로 시간순.**

## 이 파일의 진짜 목적

문서화가 아니다. **학습 장치다.**

코드 에이전트가 짠 코드를 읽으면 항상 말이 되게 보인다. 그래서 "이해한 느낌"만 남고
실제로는 남지 않는다. 이걸 막는 방법은 **읽기 전에 먼저 예측을 적는 것**이다.

### 작업 순서

1. **[사용자] 태스크 시작 전** — 예상 접근을 3~5줄 적는다. 틀려도 된다.
   틀린 게 오히려 좋다. 예측과 실제의 차이가 학습이 일어나는 유일한 지점이다.
2. **[에이전트] 구현**
3. **[사용자] 예측과 다른 부분만** 집중해서 본다. "내가 생각 못 한 게 왜 필요했지?"
4. **[사용자] 배운 것을 한 문단으로** 적는다. 못 적으면 아직 이해 못 한 것이다.
   그때 물어본다.

> diff가 150줄을 넘으면 태스크가 너무 컸다는 신호다. 안 읽고 넘어가는 순간부터
> 이 프로젝트는 남의 코드가 된다.

### 전부 깊게 이해할 필요는 없다

- **반드시 본인 것이어야 하는 것** — 스키마, 랭킹 수식, retrieval 파이프라인, 데이터 흐름
- **"대충 이런 역할" 수준이면 되는 것** — HTTP 재시도, 로깅 설정, CLI 파싱

면접에서 묻는 건 전자다.

## T1 — DB 스키마 구현 (2026-09-09)

**실제로 이렇게 됐다**
- `src/database/connection.py` — `DB_PATH` 상수 + `get_connection()`.
  경로는 `__file__` 기준으로 계산해서 어느 디렉토리에서 실행해도 같은 DB를 연다.
- `src/database/schema.py` — DDL 전체를 `SCHEMA_SQL` 문자열 하나로 두고
  `executescript()`로 실행. `docs/SCHEMA.md`의 DDL을 그대로 옮겼다.
- `scripts/init_db.py` — 실행 진입점. 생성 후 테이블 목록을 출력한다.
- 검증: 두 번 연속 실행해 에러 없음, 테이블 3개 + 인덱스 3개 확인,
  동일 항목 2회 `INSERT OR IGNORE` 시 1건 유지, FK 위반 시 예외 발생.

**예측과 달랐던 점 / 배운 것**
- 예측에 없던 것 두 가지가 필요했다.
  ① `PRAGMA foreign_keys = ON` — SQLite는 외래키를 **기본적으로 끈다.**
     `REFERENCES items(id)`라고 써 놔도 켜지 않으면 존재하지 않는 item_id가 그냥
     들어간다. 연결마다 켜야 하므로 `get_connection()` 안에 넣었다.
  ② DB 경로를 상대경로가 아니라 `__file__` 기준 절대경로로 계산. T8의 작업
     스케줄러는 작업 디렉토리가 다를 수 있어 `data/radar.db`가 엉뚱한 곳에 생긴다.
- `row_factory = sqlite3.Row`를 지정하면 결과를 튜플 인덱스가 아니라 컬럼명으로
  꺼낼 수 있다. 수집기가 늘어날 때 인덱스 번호로 접근하는 코드는 깨지기 쉽다.

**면접에서 이렇게 설명한다**
- 소스별 테이블을 나누지 않은 이유: 랭킹·검색이 소스를 가로지르는 연산이라
  테이블이 4개면 모든 쿼리가 4중 UNION이 되고 소스 추가마다 쿼리를 고쳐야 한다.
- `published_at` / `collected_at` 분리: 오래된 논문을 오늘 수집할 수 있으므로 둘은
  다른 의미다. "최근 3개월" 질의에서 어느 쪽을 기준으로 하느냐가 결과를 바꾼다.
- `item_metrics`가 별도 테이블인 이유: stars 같은 값을 `items` 컬럼에 넣고 매일
  UPDATE하면 어제 값이 덮어써진다. 그 시점의 star 수는 영원히 복원할 수 없으므로
  트렌드 분석의 근거가 사라진다. append-only 시계열로 쌓아야 기울기를 계산할 수 있다.
- metric을 컬럼이 아닌 값으로 저장(long format)한 이유: 지표가 늘어도 ALTER TABLE이
  필요 없다.

## T2 — arXiv 수집기 (2026-09-09)

**예측** — 미작성 (구현 전에 적지 못했다면, 아래를 읽기 전에 지금이라도 적어볼 것)

**실제로 이렇게 됐다**
- `src/collectors/arxiv.py` — `fetch()` → `parse()` → `save()` 3단계 함수.
  `fetch()`는 `requests`로 Atom 원문 **텍스트만** 반환하고, `parse()`가 그 텍스트를
  받는다. feedparser에 URL을 직접 넘기면 파싱과 네트워크가 한 함수에 묶여
  테스트가 불가능해진다. T3의 인터페이스 추출과 테스트가 이 분리에 의존한다.
- `src/config.py` — `load_sources()` 한 함수. 카테고리·건수·지연시간을 전부
  `config/sources.yaml`에서 읽는다. T4~T6이 같은 함수를 재사용한다.
- 실행: `python -m src.collectors.arxiv` (`scripts/collect.py`는 T7).
- 검증: 1회차 fetched=400 new=334, 2회차 fetched=400 **new=0**,
  raw_json 17개 키 보존, title 개행 0건, published_at NULL 0건.

**예측과 달랐던 점 / 배운 것**
- ① **arXiv ID의 버전을 떼어냈다.** `abs/2609.09158v1` → `2609.09158`.
  버전을 그대로 두면 논문이 v2로 개정될 때 `UNIQUE(source, external_id)`가
  다른 값으로 보고 **같은 논문이 두 행**이 된다. "오늘 볼 만한 10개"에서 같은 논문이
  두 번 뜨는 셈이다. 버전 포함 원본 ID는 raw_json에 그대로 남아 있다.
- ② **제목과 초록에 개행이 섞여 들어온다.** arXiv Atom은 본문을 80자에서 하드
  줄바꿈해서 보낸다. 그대로 저장하면 대시보드와 임베딩 입력이 전부 깨진다.
  `_squash()`로 연속 공백을 하나로 접었다.
- ③ **`json.dumps(entry)`가 그냥은 실패한다.** feedparser가 `published_parsed`를
  `time.struct_time`으로 넣어주는데 JSON 직렬화가 안 된다. `default=str` 필요.
- ④ 400건을 넣었는데 334건이 저장됐다. 버그가 아니라 **카테고리 교차 중복**이다.
  한 논문이 cs.LG와 cs.AI에 동시에 올라오면 DB가 알아서 1건으로 접는다.
  애플리케이션에서 중복 체크 코드를 한 줄도 쓰지 않았는데 동작한 것이 핵심이다.
- 의존성: `config/sources.yaml`을 읽으려면 PyYAML이 필요한데 requirements에
  빠져 있었다. 추가했다 (`PyYAML==6.0.3`).

**면접에서 이렇게 설명한다**
- **왜 `arxiv` 라이브러리 대신 `feedparser`인가** — arXiv API는 Atom 피드이고,
  T6의 빅테크 블로그 RSS도 같은 Atom/RSS다. `feedparser` 하나로 소스 2종을 같은
  파서로 처리할 수 있다. `arxiv` 전용 라이브러리를 쓰면 arXiv에만 쓰이는 의존성이
  하나 늘고, 블로그용 파서를 따로 또 들여야 한다.
- **중복 제거를 애플리케이션이 아니라 DB에 맡긴 이유** — 애플리케이션에서 하려면
  매 삽입 전에 SELECT로 존재 여부를 확인해야 하고(400건이면 400번의 왕복),
  그 사이에 다른 수집기가 같은 항목을 넣으면 경쟁 조건이 생긴다. `UNIQUE` 제약은
  이걸 DB 레벨에서 원자적으로, 공짜로 해결한다. 코드가 아니라 **제약이 불변식을
  보장**한다는 것이 요점이다.
  버전 제거로 중복은 막았지만, 개정판 내용이 반영되지 않는 트레이드오프가 있음. 필요해지면 updated_at 비교 후 UPSERT로 전환 가능.
- **fetch/parse/save를 나눈 이유** — `parse()`가 문자열 → 리스트의 순수 함수라
  네트워크 없이 고정 샘플로 테스트할 수 있다. 실제로 깨지는 건 API 응답 형식이
  바뀔 때의 파싱 로직이고, 그게 테스트 가치가 가장 높은 지점이다.


## T3 — BaseCollector 추상화 (2026-09-09)

**예측**
- 모든 수집기가 fetch() → parse() → save() 3단계를 갖도록
  공통 틀(BaseCollector)을 만든다
- ArxivCollector가 이 틀을 상속하도록 고친다.
  동작은 T2와 똑같아야 함 (리팩터링이라 기능 변화 없음)
- 새 코드보다 옮기는 코드가 많을 듯
- save()랑 collection_runs 기록은 소스마다 같으니 틀에 넣을 것 같다
- 모르겠는 것: 구현체가 아직 1개뿐인데 지금 뽑는 게 맞나?
**실제로 이렇게 됐다**
- `src/collectors/base.py` — `BaseCollector`. 서브클래스는 `units()` / `fetch()` /
  `parse()` 세 개만 채우고, `run()`이 순회 · 지연 · 예외 격리 · `collection_runs`
  기록을 담당한다 (템플릿 메서드).
- `src/collectors/arxiv.py` 108줄 → 76줄. 예측대로 **새 코드보다 옮긴 코드가 많다.**
- `tests/test_parsers.py` + `tests/fixtures/arxiv_sample.xml` (실제 응답 2건).
  pytest를 쓰지 않고 `unittest`로 했다. 순수 함수 몇 개 검증에 의존성을 늘릴 이유가
  없고, "표준 라이브러리 우선" 원칙에 맞다. `python -m unittest discover -s tests`.
- 검증: 리팩터링 후 실행 결과가 T2 2회차와 동일 (`fetched=400 new=0`),
  `collection_runs`에 status=success 1행, 테스트 8개 통과.

**예측과 달랐던 점 / 배운 것**
- **예측 중 하나가 틀렸다: "save()랑 collection_runs 기록은 소스마다 같으니 틀에
  넣을 것 같다."** collection_runs는 맞지만 **`save()`는 소스마다 다르다.**
  arXiv는 `items`만 쓰면 되지만 GitHub·HF는 **`item_metrics`에도 써야 한다** —
  게다가 metrics를 넣으려면 방금 INSERT한 행의 `item_id`가 필요해서 저장 흐름의
  구조 자체가 다르다. arXiv 하나만 보고 `save()`를 통일했다면 T4에서 뜯어냈을 것이다.
  → 그래서 base의 `save()`는 `items` 삽입까지만 하고, T4에서 확장한다.
  이게 "구현체 2개 뒤에 추출한다"는 규칙이 막으려는 실패의 실제 사례다.
- **"구현체 1개인데 지금 뽑는 게 맞나"에 대한 답** — 부분적으로 맞다.
  지금 확실히 아는 것은 **실행 골격**(순회 · 예외 격리 · 실행 기록)이고 이건 소스의
  모양과 무관하다. 모르는 것은 **저장 구조**다. 그래서 아는 것만 뽑고 모르는 것은
  남겼다. 추상화 여부가 아니라 **추상화 범위**가 실제 판단 지점이었다.
- 실패 격리 검증: 존재하지 않는 카테고리를 끼워 넣어 실행 → cs.CV 성공,
  가짜 카테고리 실패, cs.RO **계속 진행**, `collection_runs`에 status=`partial`과
  error_message 기록 확인. (검증용 행은 이후 삭제)

**T2 기록 정정**
- T2에 "arXiv가 제목과 초록을 80자에서 하드 줄바꿈해 보낸다"고 적었는데 **과장이다.**
  실제로 세어 보니 334건 중 **제목 0건, 초록 8건(2.4%)**만 개행을 포함했다.
  `_squash()`는 여전히 필요하지만(그 8건이 실제로 존재한다) 이유는 "arXiv의 하드
  줄바꿈"이 아니라 "일부 저자가 초록에 직접 넣은 줄바꿈"이다.
  → 교훈: 정규화 코드를 넣었으면 **몇 건에 실제로 영향을 주는지 세어 봐야 한다.**
  안 세면 근거 없는 방어 코드와 구분되지 않는다.

**면접에서 이렇게 설명한다**
- **왜 지금 추상화했는가** — 전부 뽑은 게 아니라 **소스 모양과 무관한 부분만** 뽑았다.
  실행 골격은 arXiv 하나만 봐도 확정할 수 있지만, 저장 구조는 metrics를 쓰는 소스를
  만들어 보기 전에는 알 수 없어서 남겼다.
- **fetch/parse/save 분리가 테스트에 주는 이점** — `parse()`가 문자열 → dict 리스트의
  순수 함수라 고정 fixture로 검증할 수 있다. 실제로 깨지는 사고는 API 응답 형식
  변경이고, 네트워크를 타는 테스트는 느리고 불안정해서 그 사고를 못 잡는다.
  fixture 테스트는 0.02초에 8개가 돈다.

## T4 — GitHub 수집기 (2026-09-09)

**예측**
- github에서도 정보를 가져온다. 매일 바뀌는 stars랑 forks를 append로 기록한다

**실제로 이렇게 됐다**
- `src/collectors/github.py` — Search API로 저장소 수집. `parse()`가 item dict에
  `metrics` 키를 하나 더 실어 보내고, `save()`가 `super().save()`로 items를 넣은 뒤
  `item_metrics`에 append한다.
- `src/collectors/base.py` — T3에서 예고한 대로 인터페이스를 **여기서 고쳤다.**
  `save()`가 dict를 그대로 넘기지 않고 `ITEM_COLUMNS`로 명시 필터링한다.
  덕분에 수집기가 자기 `save()`에서 쓸 여분 키를 item에 매달 수 있다.
- `.env.example` 추가. 실제 `.env`는 gitignore 대상.
- 검증: fixture로 `save()`를 두 번 호출 →
  `items` 2 → 2 (**신규 0**), `item_metrics` 4 → 8 (**새 행 추가**). 테스트 14개 통과.
  (검증 2회차의 중복 metric 행은 이후 삭제)

**예측과 달랐던 점 / 배운 것**
- ① **`INSERT OR IGNORE`는 `lastrowid`를 주지 않는다.** 이미 있는 저장소는 삽입이
  무시되므로 방금 넣은 행의 id를 알 수 없다. 그런데 metrics를 쓰려면 `item_id`가
  **반드시** 필요하다. → `external_id`로 되찾는 SELECT가 한 번 더 필요하다.
  T3에서 "저장 구조가 다르다"고 남겨둔 부분이 정확히 이 지점이었다.
- ② **자격증명을 `__init__`에서 읽으면 `parse()`를 테스트할 수 없다.**
  처음에 `self.token = os.environ["GITHUB_TOKEN"]`을 생성자에 넣었더니, 토큰 없는
  환경에서는 **객체 생성 자체가 실패**해서 순수 함수인 `parse()`조차 못 돌린다.
  토큰 읽기를 I/O 단계인 `fetch()`로 내렸다. fetch/parse 분리의 이유가 "테스트
  편의"만이 아니라 **자격증명 경계**이기도 하다는 것을 여기서 알았다.
- ③ GitHub Search API는 core의 시간당 5000회와 **별도 예산**을 쓴다(인증 시 분당 30회).
  그래서 로그에 남기는 `X-RateLimit-Remaining`은 search 예산의 잔량이다.

**면접에서 이렇게 설명한다**
- **items와 item_metrics의 재실행 동작이 왜 달라야 하는가** — 두 테이블이 답하는
  질문이 다르다. `items`는 "이 저장소가 무엇인가"이고 이건 변하지 않으므로 두 번째
  수집에서 새 행이 생기면 그게 버그다. `item_metrics`는 "이 저장소가 그 시점에 star가
  몇 개였나"이고 이건 매 수집마다 **다른 사실**이므로 새 행이 안 생기면 그게 버그다.
  즉 `items`는 멱등해야 하고 `item_metrics`는 멱등하면 안 된다.
  같은 실행에서 한 테이블은 `INSERT OR IGNORE`, 다른 테이블은 그냥 `INSERT`인 이유다.
- 이걸 하나의 테이블로 합쳤다면 star 수를 UPDATE해야 하고, 그 순간 어제 값이 사라져
  Phase 3의 트렌드 계산이 불가능해진다.

**라이브 검증 (토큰 수령 후)**
- 1회차 `fetched=150 new=146`, 2회차 `fetched=150 **new=0**`.
- `item_metrics` 604행 / 고유 item 148개. `collection_runs` 2행 모두 status=success.
- rate limit 로그가 `29/30 left`부터 찍혔다. 예상대로 Search는 core의 5000/시간이
  아니라 **분당 30회** 예산이다. 소스가 늘어도 GitHub만은 쿼리 수를 신경 써야 한다.
- 관찰: 두 쿼리에 동시에 걸리는 저장소는 **한 실행에서 metric 샘플이 2번** 쌓인다
  (150건 중 4쌍이 그랬다). 버그는 아니지만 Phase 3에서 기울기를 계산할 때
  "하루 1샘플"을 가정하면 안 된다는 뜻이다. 날짜별 집계 시 평균이나 최신값을 쓸 것.

## T5 — Hugging Face 수집기 (2026-09-09)

**예측**
- HuggingFace도 BaseCollector를 상속해서 구현체를 만든다
- 구조는 GitHub과 거의 같을 것: items 저장 → item_id 되찾기 → item_metrics
- downloads, likes가 metrics로 들어간다
- units()는 sources.yaml의 tasks 5개
- T4에서 save()를 이미 고쳤으니 base는 안 건드릴 것 같다
- 모르겠는 것: HF는 인증이 필요한가? GitHub처럼 rate limit이 있나?

**실제로 이렇게 됐다**
- `src/collectors/huggingface.py` — `units()` / `fetch()` / `parse()` **3개만** 구현.
  70줄이고 `save()`는 아예 없다.
- 검증: 1회차 `fetched=100 new=100`, 2회차 `fetched=100 **new=0**`,
  `item_metrics`에 downloads/likes 각 200행(모델 100개 × 2회). 테스트 20개 통과.
- 현재 DB: arxiv 334 / github 148 / huggingface 100 = **582건**.

**예측과 달랐던 점 / 배운 것**
- **예측 하나가 빗나갔다: "T4에서 save()를 이미 고쳤으니 base는 안 건드릴 것 같다."**
  실제로는 **base를 또 고쳤다.** T4에서는 metrics 저장 로직이 `github.py` 안에 있었는데,
  HF도 똑같이 필요해지면서 **같은 코드를 두 번째로 쓰게 되는 순간**이 왔다.
  그래서 `_save_metrics()` / `_item_ids()`를 base로 올렸다.
  → `github.py` 125줄 → 90줄, `huggingface.py`는 `save()`를 안 써서 70줄.
  이게 프로젝트 규칙 "**구현체를 2개 만든 뒤에 공통점을 추출한다**"가 실제로 발동한
  지점이다. T3에서 미룬 판단이 여기서 근거를 갖고 해결됐다.
  T4 시점에 미리 뽑았다면 HF의 metrics 이름이 stars/forks가 아니라
  downloads/likes라는 걸 모른 채 추상화했을 것이다.
- base의 `save()`는 이제 `item.get("metrics", {})`로 처리한다. arXiv는 metrics가
  없으므로 그냥 빠져나간다 — 분기를 넣은 게 아니라 **없으면 없는 대로 동작**한다.
- **"HF는 인증이 필요한가?"** → 공개 모델 목록은 **토큰 없이 된다.** GitHub과 달리
  `Authorization` 헤더가 없어도 200이 온다. 그래서 `.env` 의존성이 없다.
- **list 엔드포인트에는 description이 없다.** 모델 카드는 모델당 별도 요청이라
  100건이면 요청이 100번 더 든다. `summary`는 **NULL로 비워 뒀다.**
  없는 걸 tags로 지어내는 것보다 비어 있는 편이 낫다. Phase 2에서 임베딩 입력이
  부족하면 그때 모델 카드를 가져온다.
- 관찰: `sort=lastModified`는 **몇 분 전에 올라온 모델**을 준다. downloads 0, likes 0이
  대부분이라 "관심도" 신호로는 약하다. 지금은 `sources.yaml` 설정을 그대로 따랐고,
  정렬 기준 변경은 Phase 2 랭킹의 문제로 남긴다.

**면접에서 이렇게 설명한다**
- **3개 수집기가 같은 인터페이스로 동작한다** — 각 수집기가 구현하는 건
  "무엇을 순회하고(`units`), 어떻게 가져오고(`fetch`), 어떻게 우리 스키마로
  바꾸는가(`parse`)" 뿐이다. 순회 · 지연 · 예외 격리 · 실행 기록 · items 저장 ·
  metrics append는 전부 base에 한 번만 있다.
- **추상화를 세 번에 걸쳐 만들었다** — T3에서 실행 골격만, T4에서 여분 키 필터링,
  T5에서 metrics 저장. 매번 **구현체가 실제로 요구할 때** 올렸고, 미리 설계하지
  않았다. 그래서 쓰이지 않는 확장 지점이 하나도 없다.

## T5 후속 — HF 정렬 기준을 downloads로 교체 (2026-09-09)

**계기**
사용자가 "`sort=lastModified`라 downloads가 대부분 0인 게 걸린다. metrics 히스토리는
못 되돌리니 지금 정하는 게 맞다"고 지적. 측정해 보니 **문제가 예상보다 컸다.**

**측정 결과**
| | `lastModified` | `downloads` |
|---|---|---|
| 20건이 덮는 시간 범위 | **5.5시간** | — |
| downloads 중위값 | **0** (20/20이 0) | **215,580** (0건 없음) |

**진짜 문제는 신호 세기가 아니라 표본 집단의 이탈이었다**
20건이 5.5시간을 덮는다는 건 task당 하루 ~87개 모델이 수정된다는 뜻이고, 따라서
**내일의 상위 20건은 오늘과 완전히 다른 모델**이다. 그런데 `_save_metrics()`는
이번 fetch에 나온 항목만 기록하므로, 각 모델은 **평생 metric 샘플이 1개**뿐이다.
점 1개짜리 시계열은 기울기가 없다 → **Phase 3 트렌드 분석이 원리적으로 불가능.**

T5 기록에서 이걸 "Phase 2 랭킹의 문제"로 적었는데 **잘못된 분류였다.**
랭킹 입력의 품질 문제가 아니라 **Phase 1 데이터 축적 자체의 결함**이다.

**왜 교체(추가가 아니라)인가 — 비대칭**
신규 모델 발굴 경로는 **나중에 추가해도 잃는 게 없다.** 반면 안정적 표본을 오늘
샘플링하지 않으면 그 히스토리는 **영구히 사라진다.** 되돌릴 수 없는 쪽을 먼저 막았다.
`downloads` 상위 20건은 `facebook/detr-resnet-50`처럼 정착된 모델이라 몇 주간 거의
그대로 유지된다 → 같은 모델이 반복 샘플링된다.

**변경 내용**
- `config/sources.yaml`의 `sort: lastModified` → `downloads`. **코드 변경 없음.**
- fixture 재수집. downloads 정렬 응답은 키 구성이 다르다 (`lastModified` 없음,
  `library_name` 있음). 기존 fixture는 실제 수집 형태를 반영하지 못했다.
  테스트에 `downloads > 0` 단정을 추가해 0짜리 응답으로 되돌아가면 깨지게 했다.
- 검증: 1회차 new=99, 2회차 **new=0**. 상위 5개가 16.2M / 15.2M / 12.4M downloads로
  샘플 2개씩 확보. HF items 199건 = 신규 cohort 145 + 기존 잔재 54.
- 기존 `lastModified` 시절 항목 54건(downloads=0)은 **지우지 않았다.** raw_json이
  남아 있고 해가 없다. Phase 2 랭킹에서 자연히 하위로 밀린다.

**면접에서 이렇게 설명한다**
- 수집기의 **정렬 기준이 곧 시계열의 표본 설계**다. 정렬을 recency로 두면 매일 다른
  모집단을 1회씩 관측하게 되어 종단 데이터가 아니라 단면 데이터만 쌓인다.
  트렌드를 보려면 **같은 대상을 반복 관측**해야 하고, 그건 파서나 스키마가 아니라
  쿼리 파라미터 한 줄이 결정한다.
- 되돌릴 수 있는 결정(발굴 경로 추가)과 되돌릴 수 없는 결정(과거 시점 지표)을
  구분해서, 되돌릴 수 없는 쪽을 먼저 확정했다.

## T8 — 스케줄러 등록 (2026-09-09)

**T7보다 먼저 한 이유**
스케줄러가 안 돌면 하루가 지날 때마다 복구 불가능한 metrics 손실이다 (T5 후속에서
배운 것과 같은 비대칭). 완료 판정인 "7일 연속 자동 수집"의 시계도 등록 시점부터
돈다. T7의 요약 출력은 나중에 붙여도 아무것도 잃지 않는다.

**실제로 이렇게 됐다**
- `scripts/collect.py` 56줄 — 수집기 3개를 순서대로 호출. **임시 경로를 쓰지 않고
  T7의 최종 경로를 그대로 썼다.** 스케줄러 작업은 스크립트 경로를 하드코딩하므로,
  임시 경로로 등록하면 T7이 `collect.py`를 만드는 순간 스케줄러는 계속 옛 스크립트를
  돌게 된다. T7은 이제 내용만 채우면 된다.
- `docs/SCHEDULER.md` — 등록 명령과 각 설정의 이유.
- 검증: 수동 트리거 → `LastTaskResult=0`, 21초에 650건 처리, arxiv 신규 5건,
  `collection_runs` 3행 전부 success, 로그 파일 생성. 다음 실행 2026-09-10 08:00.

**예측과 달랐던 점 / 배운 것**
- ① **`schtasks`로는 작업 디렉토리를 지정할 수 없다.** PowerShell의
  `Register-ScheduledTask`에는 `-WorkingDirectory`가 있다. 그래서 후자를 썼다.
- ② **작업 디렉토리가 왜 중요한지가 예상과 달랐다.** PHASE1에는 "상대 경로 깨짐
  방지"라고만 적혀 있는데, 우리 코드의 DB·config 경로는 이미 `__file__` 기준이라
  cwd와 무관하다. 실제로 cwd에 의존하는 건 **`load_dotenv()`**다. 이건 cwd에서
  위로 올라가며 `.env`를 찾는다. 작업 디렉토리를 안 잡으면 `GITHUB_TOKEN`을 못 읽어
  **GitHub 수집기만 조용히 실패**한다. 이번 실행에서 github이 정상 동작한 것으로
  실증됐다.
- ③ `-StartWhenAvailable`을 넣었다. 08:00에 PC가 꺼져 있으면 기본 동작은 **그날을
  그냥 건너뛴다.** 노트북에서 이건 흔한 일이고, 건너뛴 하루의 metrics는 영구 손실이다.
- ④ 로그 `FileHandler`에 `encoding="utf-8"`을 명시했다. Windows 기본은 cp949라
  비ASCII 논문 제목에서 터진다.

**면접에서 이렇게 설명한다**
- 자동화의 실패는 **조용하다.** 수동 실행에서는 잘 되던 게 스케줄러에서 깨지는 이유는
  거의 항상 **환경 차이**(PATH, 작업 디렉토리, 인코딩)다. 그래서 인터프리터를 절대
  경로로 박고, 작업 디렉토리를 명시하고, 인코딩을 명시했다.
- 로그를 파일로 남긴 이유: 스케줄러 실행의 콘솔 출력은 아무도 보지 않는다.
  `LastTaskResult=0`은 "파이썬이 0으로 끝났다"만 말해줄 뿐 무엇을 수집했는지는
  로그와 `collection_runs`에만 있다.
