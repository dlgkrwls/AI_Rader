# Phase 1 — 수집 파이프라인

## 이 Phase의 목표

기능이 아니라 **데이터 축적의 시작**이다.

Phase 3의 트렌드 분석은 Phase 1에서 시작된 기록에 전적으로 의존한다. 오늘 수집기를
돌리지 않으면 두 달 뒤 트렌드 화면에 그릴 데이터가 존재하지 않는다. GitHub star 수는
그 시점의 값을 영원히 복원할 수 없다.

> **정교한 수집기를 3주간 만드는 것보다, 허술한 수집기를 오늘 돌리는 것이 낫다.**

완료 판정: 7일 연속 자동 수집 성공 + 대시보드에서 축적 데이터 확인.

---

## T1 — DB 스키마 구현

**할 일**
`items`, `item_metrics`, `collection_runs` 3개 테이블 생성. 연결 관리 헬퍼.
스키마 정의는 `docs/SCHEMA.md` 참조.

**제약**
- ORM 없이 `sqlite3` 표준 라이브러리
- DB 파일 경로: `data/radar.db`
- 스키마는 멱등하게 (`CREATE TABLE IF NOT EXISTS`) — 재실행해도 안전해야 함

**완료 조건**
- 스크립트 실행 시 `data/radar.db` 생성
- 3개 테이블과 인덱스 존재 확인 (`.schema`로 검증)
- 두 번 실행해도 에러 없음

**사용자가 설명할 수 있어야 하는 것**
- 왜 소스별로 테이블을 나누지 않았는가
- `published_at`과 `collected_at`을 분리한 이유
- `item_metrics`가 왜 별도 테이블인가

---

## T2 — arXiv 수집기

**할 일**
지정 카테고리의 최근 논문을 수집해 `items`에 저장.

**제약**
- arXiv API는 Atom 피드 → `feedparser` 사용
- **요청 간 3초 지연 필수** (arXiv 권장, 어기면 차단됨)
- 카테고리 목록은 `config/sources.yaml`에서 읽는다 (하드코딩 금지)
- 중복은 `INSERT OR IGNORE`로 DB가 처리 (`UNIQUE(source, external_id)`)

**완료 조건**
- 실행 후 `items`에 50건 이상
- 같은 명령 재실행 시 신규 0건 (중복 제거 동작 확인)
- `raw_json`에 원본 응답이 들어 있음

**사용자가 설명할 수 있어야 하는 것**
- 왜 `arxiv` 라이브러리 대신 `feedparser`인가
- 중복 제거를 애플리케이션이 아니라 DB에 맡긴 이유

---

## T3 — BaseCollector 추상화

**할 일**
T2를 만든 **뒤에** 공통 인터페이스를 추출한다. `fetch()` → `parse()` → `save()` 3단계.

**제약**
- 순서가 중요하다. 구현체 하나 없이 먼저 추상화하면 틀린 추상화가 나온다.
- 지금은 구현체가 1개뿐이므로 **최소한으로만** 추출한다. T4/T5에서 어색하면 고친다.
- 각 수집기는 `collection_runs`에 실행 결과를 기록한다.

**완료 조건**
- arXiv 수집기가 새 인터페이스로 리팩터링되고, 동작이 T2와 동일
- `parse()`가 네트워크 없이 테스트 가능한 순수 함수 형태

**사용자가 설명할 수 있어야 하는 것**
- 왜 구현체 1개 시점이 아니라 지금 추상화하는가 (혹은 T4 뒤로 미뤄야 하는가)
- `fetch`/`parse`/`save` 분리가 테스트에 주는 이점

---

## T4 — GitHub 수집기

**할 일**
GitHub Search API로 관심 토픽의 저장소 수집.

**제약**
- **stars / forks는 `item_metrics`에 기록한다.** `items`에 넣지 않는다.
- 토큰 인증 (`.env`의 `GITHUB_TOKEN`) — 시간당 5000회
- rate limit 응답 헤더를 확인하고 남은 횟수를 로그에 남긴다
- 이 시점에서 T3의 인터페이스가 어색하면 **지금 고친다**

**완료 조건**
- `items`에 저장소 저장, `item_metrics`에 stars/forks 기록
- 두 번 실행 시 `items`는 신규 0건, `item_metrics`는 새 행 추가 (핵심 동작)

**사용자가 설명할 수 있어야 하는 것**
- items와 item_metrics의 재실행 동작이 왜 달라야 하는가

## T5 — Hugging Face 수집기

**할 일**
HF Hub API로 모델 정보 수집. downloads / likes는 `item_metrics`에.

**완료 조건**

- 인터페이스 수정이 필요했다면 그 이유가 `DECISIONS.md`에 기록됨

## T6 — 빅테크 블로그 수집기

**할 일**
OpenAI · Anthropic · Google DeepMind · Meta AI · NVIDIA · Microsoft Research 등
공식 블로그 RSS 수집.

**왜 필요한가**
GPT-6 Astra(2026-09-03) 같은 발표는 arXiv에도 GitHub에도 Hugging Face에도 올라오지
않는다. 논문·코드·모델만 수집하면 업계 최대 이슈를 통째로 놓친다.

**제약**
- `feedparser` 재사용 (arXiv와 같은 Atom/RSS)
- 소스 목록은 `config/sources.yaml` — 코드 수정 없이 추가 가능해야 함
- **피드 하나가 죽어도 나머지는 계속 수집** (예외를 소스 단위로 격리)
- 피드 본문 길이가 제각각 → `summary`는 적당히 잘라 저장, 원본은 `raw_json`에

**완료 조건**
- 최소 4개 피드에서 수집 성공
- 일부러 잘못된 URL을 넣어도 나머지 소스가 정상 수집됨

---

## T7 — 오케스트레이션 스크립트

**할 일**
`scripts/collect.py` — 모든 수집기를 순차 실행하고 결과를 `collection_runs`에 기록.

**제약**
- **한 소스의 실패가 나머지를 막지 않을 것** (이 태스크의 핵심 요구사항)
- 파일 로깅 필수: `logs/collect_YYYY-MM-DD.log`
- 종료 시 요약 출력: 소스별 수집/신규 건수, 소요 시간

**완료 조건**
- 한 번 실행으로 4개 소스 전부 수집
- 소스 하나를 강제로 실패시켜도 나머지가 완료되고 `collection_runs`에 기록됨

---

## T8 — 스케줄러 등록

**할 일**
Windows 작업 스케줄러에 매일 아침 자동 실행 등록.

**제약**
- **conda 환경의 파이썬 절대 경로**를 써야 한다. 스케줄러는 PATH가 다르다.
- 작업 디렉토리를 프로젝트 루트로 지정 (상대 경로 깨짐 방지)
- 등록 방법을 `docs/`에 기록 (재현성)

**완료 조건**
- 수동 트리거로 정상 실행 확인
- 다음 날 아침 자동 실행 로그 확인

> **이 시점부터 데이터가 자동으로 쌓이기 시작한다. Phase 1에서 가장 중요한 태스크다.**

---

## T9 — 최소 대시보드

**할 일**
Streamlit으로 수집 현황 확인 화면.

**범위**
- 최근 수집 항목 목록 (제목 / 소스 / 날짜 / 링크)
- 소스별 건수
- 최근 수집 이력 (`collection_runs`)

**하지 않을 것**
랭킹, LLM 요약, 검색, 필터 — 전부 Phase 2 이후다.

**완료 조건**
- `streamlit run`으로 실행되고 데이터가 보인다
- **매일 열어보게 된다** → 이러면 Phase 1은 성공이다
